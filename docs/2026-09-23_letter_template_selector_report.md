# Contractor letter-template selector + constrained editor — implementation report
**2026-09-23**

Scope: the handoff item "Add a contractor letter-template selector and constrained editor to the existing setup, preview and approval journey." Builds on the existing `letter_content.py` setup/preview/approve journey and reusable-approval fingerprint mechanism (both pre-existing, reused as-is, not rebuilt).

## IMPLEMENTED AND TESTED

- **Three versioned templates.** `letter_content.TEMPLATE_REGISTRY` — `friendly_introduction` ("Friendly Introduction"), `professional_and_factual` ("Professional and Factual"), `short_and_direct` ("Short and Direct"). Each supplies only an opening line, a quote-request line, and a sign-off word; the locked privacy/data-source/"how we found your details"/contact-policy footer is byte-for-byte identical across all three (`tests/test_letter_content.py::TestTemplateSelection::test_locked_footer_text_is_identical_across_every_template`).
- **Template content is replaceable without rebuilding the workflow.** The three template bodies are deliberately neutral placeholder copy (see "still needed" below) — replacing them later means editing strings in `TEMPLATE_REGISTRY`, nothing else. `template_fingerprint` now bakes in the selected template's own shell text (not just its key), so editing that copy automatically invalidates every contractor's existing approval on that template, without anyone having to remember to bump a version by hand (`tests/test_letter_content.py::test_editing_a_templates_own_wording_changes_the_fingerprint_for_everyone_on_it`, and the equivalent check at the `worker.promote_pending_approvals` level in `tests/test_worker.py::test_leaves_in_place_when_templates_own_wording_changed_since_approval`).
- **Constrained editor.** Three new contractor-editable fields — `business_intro`, `services_note` ("relevant services"), `contact_email` — alongside the pre-existing `business_name`, `phone`, `service_area_note`, `insurance_note`, `qualifications_note`. Every field has its own length limit plus a combined content budget across all of them (`MAX_TOTAL_DYNAMIC_CONTENT_LEN = 1400`), enforced in `ContractorLetterSettings.validate()`. This is a documented heuristic, not a real paginated-layout check — see "still needed."
- **Credentials/insurance treated as factual claims, not invented.** Unchanged, pre-existing behaviour, reused: `insurance_note`/`qualifications_note` are shown exactly as the contractor writes them, or not shown at all — TreeKey never invents or upgrades a claim. There is no evidence-upload workflow in this codebase; the contractor's own approval (the fingerprint mechanism) is what stands in for "requiring approval" of these specific claims in this pass.
- **No automatic claims.** None of the three templates, or the locked footer, contain "trusted", "vetted", "qualified", "insured", "free"/"complimentary", or an availability claim — enforced by `letter_content.BANNED_AUTO_CLAIM_WORDS` and scanned by `tests/test_letter_content.py::TestNoAutoAddedClaimWords` against both the raw registry text and a fully-rendered letter with every optional field blank.
- **Locked sections enforced on the server.** The footer is built entirely from server config (`TREEKEY_PRIVACY_CONTACT_EMAIL`/`TREEKEY_PRIVACY_POLICY_URL`) and fixed strings — there is no form field, for any template, that reaches it. `save_letter_settings` only ever reads named fields from the posted form; a tampering POST including `privacy_contact_email`, `footer_html`, `approved`, `approved_fingerprint`, etc. has nothing to actually override, verified by `tests/test_letter_settings_routes.py::test_locked_footer_fields_posted_by_a_tampering_client_are_never_read`.
- **Contractors never receive real homeowner identifiers via preview.** Unchanged: `render_preview_letter` only ever calls `render_letter` against fixed, clearly-fictional constants (`SAMPLE-PREVIEW`, `123 Sample Street, Sample Town, ST1 2AB`, "...illustrative example only — not a real planning application"). There is no route, query param, or form field anywhere that lets a real lead's data reach a preview — verified by `tests/test_letter_settings_routes.py::test_preview_route_takes_no_lead_identifying_input_from_the_request`, which asserts `render_preview_letter` is called with only the settings object.
- **Preview uses the same rendering path as fulfilment.** Unchanged, pre-existing: `render_preview_letter` calls the exact same `render_letter` function a real send uses.
- **Escaping and markup rejection.** Found and fixed a real gap while touching this code: `render_letter` previously interpolated every dynamic value — including contractor-supplied business name/phone/notes — into HTML with **no escaping at all**. Now every dynamic value (contractor fields AND lead-sourced address/summary/council/reference) is `html.escape`d unconditionally. On top of that, `ContractorLetterSettings.validate()` actively **rejects** any `<`/`>` character in a freeform field rather than only relying on escaping — a contractor gets a clear validation error instead of their input being silently neutralised. Both layers tested independently (`TestRejectsMarkupInjection`, `TestEscapingDefenseInDepth`).
- **Storage.** `template_key`, the three new fields, and the (unchanged-mechanism) approval fingerprint are all persisted on `contractor_letter_settings`, via 4 new idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements (same backward-compatible-migration pattern already used by `suppression.py`). `migrations/0001_letter_fulfilment.sql` updated to match.
- **Any material change invalidates approval.** Unchanged mechanism, now covering the new fields too: `upsert_contractor_settings` unconditionally resets `approved = FALSE` on any save (including a template switch), and `template_fingerprint` independently covers every field plus the template's own text — both layers re-verified by `worker.promote_pending_approvals` at promotion time, not trusted from save time.
- **Immutable per-mailing snapshot.** Unchanged, pre-existing mechanism, reused as-is: `worker.promote_pending_approvals` freezes the exact rendered HTML into `letter_obligations.approved_content_html` at promotion time; `worker.run_batch` sends only that frozen copy, never re-rendering — proven end-to-end (including with the new fields populated) by the full `tests/test_content_freezing.py` and `tests/test_letter_settings_journey.py` suites, which still pass unmodified in behaviour (only their fixtures were widened to the new column shape).
- **Integrated with existing auth/ownership/mailing gates; live sending stays disabled.** No changes to authentication (still the signed `treekey_contractor_session` cookie only), to `funding.py`'s gate, or to `letter_provider.py`/`letter_providers/registry.py`'s default dry-run/`console` provider. Nothing in this pass touches `LETTER_PROVIDER` or `LETTER_SENDING_LIVE`.
- **Tests.** 39 new tests: `tests/test_letter_content.py` (template selection, locked-footer consistency, banned-word scan, length/budget limits, markup rejection, escaping defense-in-depth, new-field rendering, fingerprint coverage) and `tests/test_letter_settings_routes.py` (new-field save flow, invalid-template-key error path, locked-field tampering, preview identifier-leakage guard, plus one in `tests/test_worker.py` for template-wording-drift invalidation). Updated (not weakened) 7 existing fixtures that hand-construct the settings row shape.

## IMPLEMENTED BUT EXTERNALLY UNVERIFIED

- **Length/content-budget limits are a heuristic, not a verified-against-real-layout guard.** There is no real paginated PDF renderer in this codebase to test against (see below) — the numeric limits (`MAX_BUSINESS_INTRO_LEN = 500`, etc., `MAX_TOTAL_DYNAMIC_CONTENT_LEN = 1400`) are a deliberately conservative estimate against the existing single-page HTML/print layout, not something verified against Nick's actual PDF pipeline. Documented as such in the code; needs revisiting once the real layout exists.
- **No database migration was run against a live database** (no live DB in this sandbox, consistent with every other change this session) — `init_letter_content_schema`'s new `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements are syntactically standard idempotent Postgres and follow the exact pattern already used (and presumably already run) for `suppression.py`'s equivalent migration, but were not executed against a real Postgres instance here.

## DECISIONS OR INPUTS STILL NEEDED

- **Final template wording.** The three templates currently contain neutral, deliberately unremarkable placeholder copy so the selector/editor/approval machinery could be built and tested now. Nick's own `TreeKey-Claude-handoff-2026-09-22.zip` (`build_letter_v2.py`, `TreeKey-branded-letter-draft-v2.pdf`) shows a considerably more developed two-page branded PDF design already in progress — reportlab-based, TreeKey brand assets, a structured page-2 GDPR notice — which was **not** reproduced or wired in here (per instruction: "do not invent a new design"). That draft itself still has several explicit unresolved placeholders of its own: `[full legal name]`, `[business correspondence address]`, `[collection date]`, `[confirm the lawful basis, and if legitimate interests, the specific interests relied upon]`, `[state exactly what information is shared with the purchasing contractor]`, `[insert the actual retention periods]`, `[insert the published privacy-notice URL]` — all things only Nick can supply, unrelated to anything built in this pass.
- **Whether/how to connect this HTML `render_letter` path to that reportlab two-page PDF design.** They are currently two separate, disconnected representations of "a TreeKey letter" — the in-app HTML preview/print flow this pass extends, and Nick's standalone branded-PDF draft script. Deciding whether the production letter renderer becomes the reportlab pipeline, an HTML-to-PDF conversion of `render_letter`, or something else is a real open design decision, not something to guess at.
- **Evidence/verification for insurance and qualification claims**, if a stronger guarantee than "shown verbatim, contractor approves it" is wanted (e.g. a document-upload/verification step) — no such workflow exists in this codebase; not invented here, since it wasn't asked for in concrete detail and would be new infrastructure.

## What was not run
No live database, no live mailing provider, no real PDF/layout renderer, no browser-rendering/visual-regression check of the HTML output — none of these exist in this sandbox and none were exercised. Nothing in this pass was deployed, approved by a real contractor, sent, or charged. `LETTER_SENDING_LIVE` and `LETTER_PROVIDER` remain at their existing safe defaults (off / `console` dry-run), untouched by this change.
